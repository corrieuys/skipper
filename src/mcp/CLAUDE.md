# src/mcp

Model Context Protocol server. Alternative to stdout signal parsing — agents call typed tools.

| file | use |
|---|---|
| `server.ts` | `DaemonMcpServer`. Streamable HTTP transport (POST `/mcp` msg, GET `/mcp` SSE, DELETE `/mcp` end). Bearer token = agent runtimeId or API key |
| `auth.ts` | Token → `AgentIdentity` resolve. Union type: `InternalAgentIdentity` (running agents) or `ExternalIdentity` (API keys). Internal-instance validity is **task-scoped**: an instance token resolves while `ai.status='running'` OR its **task** is still `running` — the instance id belongs to the task for the task's lifetime, so a live process is not 401'd when a concurrent exit handler momentarily parks `agent_instances.status` off `running` (the old "token expired mid-run" race — a root awaiting delegations while resolving an escalation). `describeTokenState()` snapshots the row states for the `mcp_auth_reject` log emitted by `server.ts` on every 401 (previously silent) |
| `tools.ts` | Internal tool definitions + impl. Three session modes: root (all tools), delegated (no phase-control), external (task management only). Delegates the task-management surface to `task-tools.ts` |
| `task-tools.ts` | Audience-tagged task-management tool registry. Each spec carries `audience: "internal" \| "external" \| "both"` (+ optional `internalRootOnly`); `registerTaskTools(server, deps, getIdentity, audience, isDelegated?)` registers the matching subset. One knob controls visibility — flip a spec's audience, no other wiring. Called with `"external"` from `registerExternalTools` and `"internal"` + the session's `isDelegated` at the end of `registerDaemonTools`. Today the internal surface is just the recurring-task pair (`list_recurring_tasks`, `run_recurring_task`), tagged `"both"` + `internalRootOnly` so only the **root** Skipper sees them; everything else is external-only. `taskToolNamesFor(audience, isDelegated?)` lists the names |
| `tools-registration.test.ts` | which tools each session mode gets |
| `slack-tools.test.ts` | what the Slack tools *do* when invoked: origin capture (which ts anchors), plus `escalate`'s `slack_warning` gates. Stubs the Slack Web API by swapping `globalThis.fetch` |
| `signal-bridge.ts` | Convert MCP tool calls → `agent:signal` events (so handlers stay one path) |

Role-based tool visibility locked at session create. Three identity types:
- **Internal root**: full tool set (notes, artifacts, delegation, escalation, phase control, global store) plus the recurring-task pair (`list_recurring_tasks`, `run_recurring_task`) from `task-tools.ts` — so the root Skipper can trigger another approved recurring task's run (optional one-off `prompt` → that run's `run_input`), independent of its schedule. `run_recurring_task` also **carries the calling task's Slack thread** to the new run by default: it reads the caller's `slack_origin` (`readTaskSlackOrigin`, internal identity only) and passes it as `runTaskNow`'s `slackOrigin`, so the new run's escalations/reviews/completion notice continue in the same thread — the result's `slack_thread_continued` reports whether it did. `continue_slack_thread: false` opts out; external callers have no task context, so they never inherit. `list_recurring_tasks` reports **`active_runs`** per recurring task (count of its runs currently approved/running/paused), and the prompt tells the root Skipper to check it first and skip triggering when non-zero — the soft guard against a **reset** re-firing a run that is still in flight (a respawned Skipper can't see its own earlier tool calls, so `active_runs` is its only signal). `runTaskNow` itself stays unguarded (manual "Run Now" is deliberately allowed to overlap), so this is prompt-level, not enforced.
- **Internal delegated**: same minus phase-lifecycle tools AND the recurring-task pair (both `internalRootOnly`). Also applies to **one-off runs** — an instance flagged `state_metadata.oneshot=true` (operator resume on a completed task) is treated as delegated by `server.ts:isDelegatedRuntime`, so phase/task-lifecycle tools are omitted.

`delegate` / `delegate_batch` take an optional `working_directory` per child: an absolute path that must already exist, validated by `validateWorkingDirectory` (`orchestrator/delegation-manager.ts`) before any row is written. Unlike the task-level `working_directory`, which is prompt-only, this sets the child's prompt line AND the cwd its process starts in, so the child sees that repo's own `CLAUDE.md` / `.claude` config. Omit it to inherit the task's path and the orchestrator cwd. Persisted on `delegations.working_directory` so retries and `delegate_resume` land in the same place. Caveat: for the experimental `grok` provider the spawn-time `.grok/config.toml` patch (`agents/mcp-spawn-helper.ts`) is written into that directory rather than Skipper's, and restored on exit.

`create_file_artifact({ name, path, description? })` lets an agent (root, delegated and solo alike; also in the custom-agent catalogue + `SOLO_ESSENTIAL_TOOLS`) attach a file it generated on disk (screenshot, PDF, archive, any binary) as a file artifact. `path` must be absolute and point to an existing regular file on the daemon host under the 25 MB cap (`MAX_FILE_ARTIFACT_BYTES`); relative paths, missing files, directories and oversize files are refused with a plain error and nothing is written. The bytes are copied into the artifact store via `createFileArtifact` (`kind: 'upload'`, `source` = the caller's template agent id, mime sniffed by magic bytes for images else `mimeFromExtension` from `artifact-files.ts`, fallback octet-stream), then `RealtimeSessionManager.ingestAgentArtifact` (optional `DaemonDeps.realtimeSessionManager`, wired in `index.ts`) lands the timeline row already fed so it never enters the INPUT_FEED and nothing about the task changes. Returns the same file-shape JSON `get_artifact` returns (`fileArtifactMeta`: id, storage 'file', kind, name, version, mime, bytes, width, height, sha256, path, description).

`get_artifact` / `list_artifacts` know about **file artifacts** (operator uploads and agent attachments, `storage='file'`, kind `upload`): list rows add `storage`, `mime`, `bytes`, `width`, `height`; `get_artifact` on a file artifact returns `{ storage:'file', kind, name, version, mime, bytes, width, height, sha256, path, description, note }` and never the bytes — the agent opens `path` with its own file/image tool (both tool descriptions say so). One addition for **custom (in-process) agents**, which have no file tool: when the calling runtime's template agent type is `custom:*` (`isCustomAgentRuntime`, one `agents.type` lookup) and the artifact is an image, the result content also carries an MCP `image` block (base64 + mimeType) beside the JSON text.

`post_message` records a short, plain-language update for the human operator (`src/messages/`). Registered on every internal session — root, delegated AND solo (single/custom agents) — any agent can notice something worth surfacing; it is no longer gated by `--experimental`, and the solo tool profile (`SOLO_ESSENTIAL_TOOLS` + `prompts/mcp-tools-single.md`) includes it. One-way: nothing reads messages back into a prompt, so there is no list/get counterpart. Writing rules live in `prompts/commands-messages.md`.

Global-store tools (`set_global_value`, `get_global_value`, `query_global_store`, `delete_global_value`) read/write the cross-task `global_store` table via `GlobalStoreManager` (`src/global-store/`). Available to root + delegated. Prompts instruct agents to use them only when a task/phase/template explicitly asks.

Slack tools (`slack_send_message`, `slack_send_dm`, `slack_read_channel`) post/read as the Skipper Slack app via the bot token. **Root-only**, like the phase-lifecycle tools — only Skipper talks via Slack, so a task's thread stays one voice; delegated children reach the operator by escalating, which the push forwards into the same thread. Registered on a session only when not delegated + `isExperimental()` + `isSlackConfigured(db)` + the task's team has `slackEnabled` (see [../slack/CLAUDE.md](../slack/CLAUDE.md)). The two **send** tools also `stampTaskSlackOrigin` — a task with no Slack origin yet adopts the thread the agent just posted into, so its escalations/reviews/completion notice follow (first write wins; a slash-command origin is never replaced). When a send is the one that captured the origin, its result carries `thread_ts` + a `note` explaining what the thread now means — the live agent's only way to learn this, since prompts aren't rebuilt mid-turn. A run with an origin gets a `SLACK ORIGIN` block on later prompt builds. `escalate` returns a `slack_warning` when the question exceeds `SLACK_ESCALATION_SOFT_LIMIT` **and** the task has a Slack origin — Slack clips the escalation block at `ESCALATION_TEXT_LIMIT` and agents put the ask last, so the operator would answer a fragment. Both constants come from `slack/blocks.ts`; nothing here restates them as a literal. It warns rather than rejects (an escalating agent is already stuck, and the full text is readable in the web UI) and is the only surface that reaches an agent whose prompt predates the origin.
- **External** (API key): task management + discovery — `create_task`, `get_task`, `list_tasks`, `list_active_tasks`, `update_task` (draft-only edit), `approve_task`, `pause_task`, `resume_task` (paused→running), `cancel_task`, `complete_task`, `list_teams`, plus recurring tasks: `list_recurring_tasks`, `run_recurring_task` (one-off "Run Now" on an approved recurring task, optional `prompt` → the run's `run_input`; mirrors the Slack slash-command path — impl via `ScheduledTaskScheduler.runTaskNow`, the internal class name), plus two **writes into a task**: `create_note` and `create_artifact`. All defined in `task-tools.ts`, tagged `audience: "external"`, so none are exposed to internal agents. The two task-list tools return **newest-first, paginated** results — `{ tasks, pagination: { page, page_size, total, total_pages, has_more } }`, `page` 1-based, `page_size` default 20 / max 100 — so a caller with hundreds of tasks pages through bounded chunks.

`create_note` / `create_artifact` share their names with the internal tools in `tools.ts` but are different specs. The internal pair take the task from the caller's identity and write **as that agent**; the external pair take an explicit `task_id` and write **as the operator** — `create_note` goes through `TaskScheduler.addExternalNote` (the same call a Slack thread reply makes: `source='user'`, attributed to the team entrypoint agent, emits `task:note_added`), so it lands exactly as a note typed into the UI panel, including injection into the next prompt build. It errors on a task with no team, since there is then no agent to attribute the row to. `create_artifact` stamps `created_by_agent_id='api'`, matching `POST /data/tasks/:id/artifacts`. A session is either internal or external, so only one tool of each name is ever registered.

Operator-defined tools (`src/custom-tools`) are registered on every internal
session, resolved per instance from what the custom agent definition and the team
agent each grant — so a CLI agent can be given one. They are registered last, so a
name that slipped past the reserved-name guard cannot shadow a built-in.

## In-process consumers

Custom agents (`src/custom-agents/`) run inside the daemon but still reach these
tools over `POST /mcp` on localhost, with the instance id as the bearer token,
rather than calling `tools.ts` directly. That keeps one set of rules: the
root/delegated split above still decides what a session sees, and `signal-bridge`
dedup still applies. The agent's own config narrows that further — only the tool
names its definition enables are put in front of the model.

## External access

External agents authenticate with API keys (managed via `/api/api-keys`, or the API Keys panel on `/config` under `--experimental`). Configure in `.mcp.json`:
```json
{ "mcpServers": { "skipper": { "type": "streamableHttp", "url": "http://localhost:5005/mcp", "headers": { "Authorization": "Bearer <api-key>" } } } }
```

The same keys authenticate the JSON data API — every `/data/*` route requires `Authorization: Bearer <api-key>` (see [../routes/CLAUDE.md](../routes/CLAUDE.md)). Key validation is shared via `auth.ts:resolveApiKey()`.
