# src/tasks

Task CRUD + state machine.

| file | use |
|---|---|
| `scheduler.ts` | Task CRUD. Lifecycle: draft/approved/running/completed/failed. Unapprove, iterate, cancel, retry, resume. Phase + regression counters. `iterateTask` detaches only the **root** Skipper session (`parent_instance_id IS NULL`) so the re-run re-plans cold; delegated children keep their `session_id` and stay resumable via `delegate_resume`. **Exception: single-agent tasks** (projected `sa:<id>` team id) keep the root session too - the single agent is the sole executor with no phases/delegation, so it must resume its own conversation on iterate rather than lose context (`isSoloTeamId(task.team_id)` guard; task-runner resumes the root when `session_id` survives). Because that resume continues the agent's OWN session, `prompt-builder.ts` sends a solo resume a "CONTINUING YOUR OWN SESSION" preamble and skips both the cold-start solo framing and the team-style "previous attempt / read the notes" preamble — otherwise the resumed agent dissociates and answers as if it has no memory of its own prior turns. It also sends **only the latest iteration instruction** (the text after the last `ITERATION N (ts):` marker `iterateTask` appends), not the whole accumulated description — the earlier description is already in the resumed conversation, and re-sending it makes the agent (weak models especially) re-do the ORIGINAL task instead of the new ask (`latestIterationInstruction`). `addExternalNote(taskId, content, source)` records a note authored outside the agent runtime (e.g. a human reply in the origin Slack thread — see [../slack/CLAUDE.md](../slack/CLAUDE.md)), attributed to the team entrypoint agent for the FK |
| `scheduled-scheduler.ts` | Scheduled task firing → creates task. Two mutually exclusive schedule modes: fixed interval (`schedule_unit`/`schedule_amount`) or weekly matrix (`schedule_matrix`, JSON 7x24 of 0/1, local time, fires at top of enabled hour via `calculateNextRunFromMatrix`). Cron firing (`manager-daemon.ts:fireStandardScheduledTask`) is **singleton per scheduled task**: it skips a new run while a prior run is still active (`approved`/`running`/`paused`) and still advances `next_run_at` past the skipped slot, so a sleep/wake catch-up burst of overdue slots can't spin up overlapping runs of the same recurring task. Manual "Run Now" (`runTaskNow`) is intentionally not guarded. `findScheduledTaskBySlashCommand` matches a Slack slash command bound via `task_config.slashCommand` (runs the task now via Socket Mode - see [../slack/CLAUDE.md](../slack/CLAUDE.md)). `runTaskNow(id, taskScheduler, runInput?, { slackOrigin? })` stamps the optional per-run input (`tasks.run_input`, injected into the run prompt) and, for Slack-triggered runs, `task_config.slack_origin` (so the run can reply to Slack). `global_store_instructions`: free-text global-store contract merged into every spawned run's `task_config` and injected into the root prompt by `prompt-builder.ts`. Webhook trigger lifecycle (`enableWebhook`/`regenerateWebhookKey`/`disableWebhook` on `webhook_key`; `setWebhookDebounce` leading-edge debounce in minutes, floor 1, enforced by `runWebhookTask` - ignored webhooks restamp the window) - public trigger URL relayed via connect, validated in `connect/resources.ts` |

Lifecycle states + transitions documented in root [CLAUDE.md](../../CLAUDE.md).
